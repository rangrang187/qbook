## 1. Implementation Overview（实现概述）

### 1.1 本次实现目标与范围

V1 要交付一个可以独立调用和测试的订单簿组件：调用者依次交给它新增、修改、成交、撤单或聚合价位事件，它维护一个品种的当前状态，并能立即返回最高买价、最低卖价及对应总量。订单簿反映外部已经发生的事件；即使买价高于卖价，也不会自行撮合成交。

| Backlog 任务 | 本版要实现的能力 | 可检查的交付结果 |
|---|---|---|
| V1-01 新增、存储与同步快照 | 建立单品种绑定、订单所有权、ID 查找和价位顺序；实现新增及只读观察。 | `Orderbook`、`ApplyResult`、`qbook_core` 和新增测试；空簿、最优一档、内存估计可核对。 |
| V1-02 修改订单 | 将剩余数量设置为新总量；同价保序，改价进目标末尾，非正新量删除。 | 改单正常、忽略、溢出及删除场景有明确预期。 |
| V1-03 成交与撤单 | 根据订单 ID 扣减，部分保留，恰好或超额移除。 | 双侧成交、单侧缺失、撤单和首中尾删除均保持索引与价位一致。 |
| V1-04 L2 价位 | 维护按价格给出的绝对总量；成交只更新最近事件时间。 | L2 不建立虚构订单，20→8→成交3→0 的状态变化正确。 |
| V1-05 核心回归与异常、移动安全 | 组合前四项，验证多品种隔离、移动、外层表扩容及分配失败回滚。 | 核心回归、受控失败测试和实际版本验收记录。 |

V1 提供的是**同步快照**：调用 `OnSnapshot()` 当场读取当前状态。定时生成快照、多品种调度、队列收发和原始记录转交属于 V2 的 `BookThread`；Parquet 和正式服务入口属于 V3；指标发布及 UI 属于 V4；性能实验与数值达标判断属于 V5。

因此，本版不创建 `BookThread`、网络发布者、ZMQ 接收、Writer、正式 `main.cpp`、UI 或 benchmark。V1 的多品种测试只用一个测试内的 `qlib::map<std::uint32_t, Orderbook>`，不能将它描述成已经实现的运行阶段。输入不变的测试也不能替代原始事件文件验收。

### 1.4 开发环境、依赖与工具链

沿用已选基线：Linux / WSL2、x86-64、小端、8 字节指针、C++23、CMake 3.28 或以上、Ninja 和固定 Catch2 v3。编译器、标准库和 qlib 的真实版本写入 `docs/releases/V1.md`，不能直接沿用参考作者的环境信息。

`third_party/qlib` 通过 `add_subdirectory` 提供 `qlib::qlib`；关闭 `QLIB_BUILD_TESTS`，只运行 qbook 本版需要的契约与业务测试。Catch2 仍按 V0 的固定源码方式接入，V1 不为了新增业务测试升级依赖。无测试构建可以不引入 Catch2；核心构建无需 ZeroMQ、Arrow、Parquet 或 Node。

常规构建与测试只使用 `build/debug`。V1-05 如在支持的环境使用 ASan/UBSan 检查悬空指针、生命周期和整数错误，按第 5.2 节单独使用一个配置隔离目录；它的编译选项不同，不是为重复跑同一组普通测试而新增目录。

### 1.5 实现约束与完成条件

**实现约束。** 一个 `Orderbook` 固定一个品种和一种模式，所有读写由同一个所有者线程顺序执行。事件以 `const&` 输入，只有 hive 中保存的订单副本可以变化。正常业务忽略通过 `ApplyResult` 返回并更新时间；内部契约错误或分配失败抛出异常，不改称输入拒绝，也不写入 `feed_dropped`。

**修改边界。** 新增本版生产源码、测试和必要文档，保留用户已有修改。生产类不为测试增加在线查询接口；只读观察器定义在 `tests/`。不修改 qlib 公共 API 来制造故障，不引入通用事务、故障注入框架或全簿复制。提交、推送和后续版本执行遵循实际用户授权；本次请求只生成此实现计划。

**完成条件。** V1-01～V1-05 均有实际代码和已执行测试证据；固定用例、逐项业务语义、不变量、移动和关键准备失败路径通过；编译和测试目标无空实现；发布记录区分通过、失败、未执行。完成第 5.2 节的产物清理和文档同步后，才可将 V1 标为完成。仅有本计划不得改变 Backlog 的任务状态。

### 2.2 各模块需要实现的类与组件

| 名称 | 角色 | 关系和边界 |
|---|---|---|
| `qbook::Orderbook` | 本版唯一生产业务类。 | 拥有订单和价位状态；借用输入，不拥有上游或文件模块。 |
| `ApplyStatus`、`IgnoreReason`、`ApplyResult` | 按值返回的业务结果。 | 只报告是否更新及忽略原因，没有生命周期管理和线程职责。 |
| `BookMode` | V0 定义的模式枚举。 | 直接复用，不在 Orderbook 头文件重新定义。 |
| `qlib::price_level` | 价位的数量及链表首尾。 | 直接使用；逐笔模式借用订单地址，L2 首尾始终为空。 |
| `qbook::testing::OrderbookInspector` | 测试内只读观察器。 | 仅测试定义和调用；帮助证明完整状态，快照只含一档不足以证明 FIFO。 |
| 分配失败测试辅助 | 专用测试程序的局部工具。 | 仅用固定计数和开关制造指定分配失败，不成为 qbook 的运行配置。 |

FIFO 在这里指“同方向、同价格订单的先后顺序”。节点间的 `prev/next` 存在订单自身中，称为侵入式链表；它们只借用邻居地址，不能负责释放邻居。

### 2.3 类与源文件、头文件的对应关系

`Orderbook.h` 公开事件入口、同步快照、`size()`、`MemoryBytes()` 和结果类型；私有成员与必要的私有函数也在同一声明中。业务实现放在 `Orderbook.cpp`，不为了五个 Backlog 任务拆成五个相互依赖的生产类。饱和算术等短辅助可以放在实现文件内部，若需边界测试则通过最小的测试访问安排验证，不新增公共产品接口。

测试友元采用一致声明：头文件无条件前向声明 `qbook::testing::OrderbookInspector`，在类中声明友元；具体定义只在 `tests/support/OrderbookInspector.h`。不能用测试宏让不同编译单元看到不同的类定义。观察器不修改私有状态，也不持有超过本次同步检查的引用或迭代器。

构建目标按实际源码组织：

| 目标 | 本版源码与链接关系 | 加入时点 |
|---|---|---|
| `qbook_support` | 保留 V0 的 Config、Runtime 和指标基础源码。 | 已有目标；不把 Orderbook 塞进其中。 |
| `qbook_core`（STATIC） | 仅 `src/Orderbook.cpp`；公开 `include/`、C++23 和 `qlib::qlib`。 | V1-01，第一批真实新增和快照实现出现时。 |
| `qbook_tests` | 保留 V0 三个测试源文件，再逐项加入本版五个普通测试文件；链接 `qbook_support`、`qbook_core`、`Catch2::Catch2WithMain`、必要的 `Threads::Threads`。 | 每项任务完成相应测试后加入。 |
| `qbook_allocation_tests` | `tests/orderbook_allocation_tests.cpp` 与 `tests/support/AllocationFailure.cpp`；链接正常 `qbook_core`、Catch2。 | V1-05；全局分配替换只存在于此可执行文件。 |

两个测试可执行文件分别通过 `catch_discover_tests` 注册，并使用不同的 `TEST_PREFIX`（例如 `unit::` 与 `allocation::`），防止用例名称冲突。分配替换没有链接到 `qbook_tests` 或生产库，不覆盖配置、线程或其他模块的内存行为。专用测试的需要来自失败机制隔离，不要求另建一套构建目录。

`BUILD_TESTING=OFF` 时只构建真实库，两个测试目标和测试辅助都不加入。V0 的 `QBOOK_BUILD_SERVICE`、`QBOOK_BUILD_BENCHMARKS` 本版仍默认关闭；本版未实现的选项如果显式开启，继续给出明确配置错误，不产生假的服务程序。

### 2.4 模块与类之间的实现依赖

生产依赖很简单：`Orderbook` 使用 `PipelineTypes.h` 中的 `BookMode`、qlib 数据/容器及标准库；没有网络、时钟调度或文件依赖。运行时的输入顺序由调用者保证，V1 测试线程就是唯一所有者。

订单由 `orders_` 拥有，`by_id_` 保存订单地址，价位首尾和订单之间的链接借用同一批地址。借用者不删除对象。价位与索引先销毁，hive 后销毁；删除单张订单时也先清除借用关系再释放其存储。默认移动只有在全部拥有成员转交资源且实际不抛异常时才成立，验证对象是这些真实类型。

测试依赖正常生产库，观察器只能读取；故障程序通过分配函数替换使真实分配失败，不能用一套复制业务算法替代生产方法。外层品种表仅用于验证 V2 将来会遇到的移动情形。

### 2.5 整体编码顺序及其原因

1. 验证 V0 的代码、固定依赖与测试入口；阅读 qlib 当前实现，确认计划中的 API 仍匹配。
2. 建立结果类型、绑定成员、容器和 `qbook_core`；先做新增、同步快照和观察工具，让后续改动都有可核对的完整状态。
3. 实现同价修改和共享删除，再实现改价准备与提交；先掌握单张订单跨价位变化，随后复用删除路径处理成交和撤单。
4. 在明确隔离的 L2 模式中设置绝对量，复用快照但不复用逐笔订单存储。
5. 组合业务序列，检验外层扩容、显式移动和实际分配失败；最后运行全部已登记测试并记录结果。

每一步只把已实现功能写成可用。尚未实现的入口可以暂不定义、不调用，不能以默认返回 `Applied` 或空函数使整版看似完成。

## 3. Module Implementation（模块实现方案）

本版只有订单簿业务模块。五项 Sprint 任务逐步完善同一个 `Orderbook`，不为每种事件再建立一套拥有订单的类。下面先交代共同的数据关系，再按函数说明一次事件如何改变这些数据；所有代码都是待实施的声明或伪代码，不能当作已经完成的实现。

### 3.1 模块实现概述

#### 3.1.1 模块实现目标

本模块接收调用者已经校验过的单个事件，更新一个品种的当前状态，并立即返回业务结果。逐笔模式按订单 ID 维护挂单；L2 模式直接维护某个价格的总量。两种模式都能同步读取最优买卖一档，满足 FR-05～FR-09 和 FR-10 的快照内容部分。

V1 不从队列收消息，不创建工作线程，不定时生成快照，也不写文件。通过测试直接调用事件方法，证明业务结果正确；以后 V2 的 Book 阶段再负责调用这些方法和转交原始记录。

#### 3.1.2 对应的 Spec 章节

| 规格依据 | 本章落实的内容 |
|---|---|
| `specs.md` 3.2～3.6 | 使用 qlib 的固定宽度字段、订单/价位关系和单品种不变量，不重新定义事件结构。 |
| `specs.md` 4.3.1、4.3.2.1 | `Orderbook` 的公开接口、私有辅助操作、所有权、结果原因、移动和异常规则。 |
| `specs.md` 5.1～5.4 | 业务忽略与致命异常分开；单线程拥有；先验证成员能力再声明不抛移动；复杂度和内存口径如实表述。 |
| `Sprint_Backlog.md` V1-01～V1-05 | 按新增与快照、修改、成交撤单、L2、组合与失败回归依次交付。 |

#### 3.1.3 需要实现的类与文件

`include/Orderbook.h` 声明 `ApplyStatus`、`IgnoreReason`、`ApplyResult` 和 `Orderbook`；`src/Orderbook.cpp` 实现业务方法和局部算术辅助函数。`ApplyResult` 只是两个枚举值组成的返回结果，没有自己的状态机或资源。

新增、修改、扣减、L2 和组合不变量测试分别进入 `tests/orderbook_add_tests.cpp`、`tests/orderbook_modify_tests.cpp`、`tests/orderbook_reduce_tests.cpp`、`tests/orderbook_l2_tests.cpp`、`tests/orderbook_invariant_tests.cpp`。只用于检查私有状态的 `tests/support/OrderbookInspector.h` 由测试持有；受控分配失败的隔离测试按第 5.3 节建立，不进入生产库。

#### 3.1.4 依赖与复用组件

直接复用 V0 的 `PipelineTypes.h` 中 `BookMode`，以及固定版本 qlib 的 `order`、`trade`、`cancel`、`level`、`book`、`price_level`、`hive`、`map`。买卖价位使用标准库 `std::map`，按价格升序排列；本版无需 ZMQ、Arrow、Parquet 或 UI 依赖。

实施前核对三个实际接口：`hive::emplace()` 返回属于当前容器的迭代器，`hive::get_iterator(pointer)` 按块定位且不能验证任意旧指针，`qlib::map::try_emplace()` 的键参数是 `Key&&`。因此插入 ID 使用临时键，移动后删除节点重新取得当前 hive 的迭代器。

### 3.2 Class Implementation（Orderbook 类实现）

#### 3.2.1 类的实现目标

`Orderbook` 把“一张订单仍然存在、它能按 ID 找到、它恰好出现在一个价位、价位合计与挂单相符”作为一件事维护。调用者只提交事件，不得分别操作索引、链表和存储。

例如同一买价已有 B1 数量 10、B2 数量 5，修改 B1 的 `new_qty=6` 后，B1 剩余量变成 6，价位总量变成 11，B1 仍排在 B2 前面。输入事件中的 `new_qty` 和其他字段保持原值，后续阶段仍可保存这个事件本身。

#### 3.2.2 类的声明与文件组织

头文件只放类型、成员和方法声明。实现文件包含整数边界检查、容器操作和错误文本；不把分配失败的测试开关放进业务类。以下声明在 V1 五项任务完成后成立；编码时随任务逐步补齐真实定义，不用返回固定结果的空函数伪装尚未完成的分支。

```cpp
namespace qbook {
namespace testing { struct OrderbookInspector; }

enum class ApplyStatus : std::uint8_t { Applied, Ignored };
enum class IgnoreReason : std::uint8_t {
  None, DuplicateId, UnknownOrder, MarketOrder, Unchanged,
  SideMismatch, QuantityOverflow, L2Trade, MissingLevel
};
struct ApplyResult {
  ApplyStatus status;
  IgnoreReason reason;
};

class Orderbook {
 public:
  Orderbook(std::uint32_t instrument_id, BookMode mode);
  Orderbook(const Orderbook&) = delete;
  Orderbook& operator=(const Orderbook&) = delete;
  Orderbook(Orderbook&&) noexcept = default;
  Orderbook& operator=(Orderbook&&) noexcept = default;
  ~Orderbook() = default;

  ApplyResult OnOrder(const qlib::order& event);
  ApplyResult OnTrade(const qlib::trade& event);
  ApplyResult OnCancel(const qlib::cancel& event);
  ApplyResult OnLevel(const qlib::level& event);
  qlib::book OnSnapshot() const;
  std::size_t size() const noexcept;
  std::size_t MemoryBytes() const noexcept;

 private:
  using OrderStore = qlib::hive<qlib::order>;
  using IdMap = qlib::map<std::int64_t, qlib::order*>;
  using PriceLevelMap = std::map<std::int64_t, qlib::price_level>;
  friend struct testing::OrderbookInspector;

  ApplyResult Add(const qlib::order& event);
  ApplyResult Modify(const qlib::order& event);
  bool Reduce(std::int64_t order_id, std::int64_t qty);
  void Erase(qlib::order* node);
  qlib::price_level& FindLevel(const qlib::order* node);
  void UnlinkOrders(qlib::order* node);
  void LinkOrders(qlib::order* node, qlib::price_level& level,
                  std::int64_t new_total) noexcept;
  void Touch(std::int64_t event_ns, std::int64_t recv_ns) noexcept;

  std::uint32_t instrument_id_;
  BookMode mode_;
  OrderStore orders_;
  IdMap by_id_;
  PriceLevelMap bids_;
  PriceLevelMap asks_;
  std::int64_t event_ns_ = 0;
  std::int64_t recv_ns_ = 0;
};
}  // namespace qbook
```

`OrderbookInspector` 的定义只在测试目录中存在，友元声明在所有构建中保持一致，避免用宏制造不同的类定义。它读取节点地址、链接、总量和容量以检查不变量，不提供线上查询接口，不向产品调用者返回可变指针。

公开声明保持 Spec 约定。对固定的 `OrderStore`、`IdMap`、`PriceLevelMap` 分别加入移动构造和移动赋值的 `std::is_nothrow_*` 编译期检查，再检查 `Orderbook` 本身；另检查 `qlib::order` 的析构不抛。只有这些前提成立，显式 `noexcept` 才有依据。不要只检查已经写了 `noexcept` 的外层类型而跳过成员。

#### 3.2.3 成员变量的具体实现

| 成员 | 类型与初始化 | 生命周期、所有权及状态约束 |
|---|---|---|
| `instrument_id_` | `std::uint32_t`，从构造参数赋值。 | 构造后绑定一个品种；0 在本版协议中可用，不擅自判错；不随事件改写。 |
| `mode_` | `BookMode`，构造时校验为 `Mbo` 或 `L2`。 | 构造后绑定一种模式；不增加运行中切换入口。 |
| `orders_` | `qlib::hive<qlib::order>`，初始为空。 | 唯一拥有挂单对象。对象地址在合法插入、其他节点删除和 hive 移动后保持有效；该对象删除后地址立即失效。L2 不创建订单对象。 |
| `by_id_` | `IdMap`，初始为空。 | 每个活订单 ID 对应一个借用指针；不拥有、不释放订单。任意插入可能使该表的引用和迭代器失效，但不会搬动指针所指的 hive 对象。 |
| `bids_`、`asks_` | `PriceLevelMap`，初始为空。 | 拥有价位节点；价位只借用订单地址。逐笔模式价位量严格为正且有首尾；L2 价位量严格为正、首尾都为空。买卖同价是两处独立状态。 |
| `event_ns_`、`recv_ns_` | `std::int64_t`，显式初始化 0。 | 保存最近一次正常返回的业务事件时间，包括 `Ignored`。不取历史最大值，不用读取快照时的时钟替换；致命异常不承诺推进。 |

声明顺序让析构先销毁价位和 ID 借用关系，再释放 hive 中的订单。链表是“侵入式”的：`prev/next` 就存在 `qlib::order` 对象内，不另行分配链表节点。节点的 `prev/next` 不拥有邻居，析构也不会自动解链；每次业务删除必须主动完成关系清理。

以下不变量在每个公开方法正常返回后成立，在受控分配失败回滚后也成立：

1. 逐笔模式 `orders_.size() == by_id_.size()`；每个活订单有唯一 ID 索引，且只属于自身方向、价格对应的一条链。
2. 一条链的 `head->prev` 和 `tail->next` 为空，前后链接互相对应，没有环；链内数量均为正，合计等于价位 `qty`，合计不超过 `INT64_MAX`。
3. 逐笔价位没有“数量为 0 但仍留在表中”的残留；最后一个节点离开就删除价位。创建过程中的临时空价位不能跨方法返回保留。
4. L2 中 `orders_`、`by_id_` 保持为空，所有价位 `head/tail` 为空，不通过虚构订单复用逐笔链表。
5. 事件对象只是调用期间借用的只读输入。新增存储副本必须将 `prev/next` 重置为空，再建立本地链接；修改状态不得反写调用者对象。

测试中的不变量扫描可以遍历所有订单和价位；生产事件路径不为每条消息执行整簿扫描。

#### 3.2.4 成员函数的具体实现

下面各表统一列出模板要求的 11 个方面。复杂度中的 `N` 为当前活订单数，`L` 为相关一侧价位数，`B` 为 hive 块数；哈希查找“平均常数”不等于最坏情况常数。所有方法的线程规则相同：仅对象的当前所有者调用，读取也不得和写入并发。

##### A. `OnOrder`：检查调用契约并分发新增或修改

| 实现维度 | 具体方案 |
|---|---|
| 函数声明与职责 | `ApplyResult OnOrder(const qlib::order& event)`；把一个逐笔订单事件交给新增或修改路径。 |
| 输入、输出与契约 | 输入已通过协议校验，品种必须相同且本簿为 `Mbo`；返回实际 `ApplyResult`，输入不变。 |
| 核心算法与数据结构 | 只检查绑定和按 `action` 分支；状态相关判断由 `Add/Modify` 执行，避免入口和私有函数各做一遍更新。 |
| 具体执行步骤 | ①检查品种、模式；②按 add/modify 调用目标方法；③得到正常结果后调用 `Touch`；④原样返回结果。未知 action 属内部误用，抛明确异常。 |
| 成员读写 | 直接读绑定字段、写最近时间；通过被调方法修改订单、ID 和价位。 |
| 对其他函数的调用 | `Add` 或 `Modify`，随后 `Touch`；不调用网络、日志计数、文件和时钟。 |
| 边界与错误处理 | 错品种/模式抛 `std::invalid_argument`，不返回业务忽略；重复等正常忽略也必须执行 `Touch`。 |
| 异常安全与状态一致性 | 检查在任何写操作前完成；准备资源失败由私有路径回滚并向上传播；异常时不要求更新时间。 |
| 时间与空间复杂度 | 分发本身 `O(1)`、额外空间 `O(1)`；整体成本取决于 `Add/Modify`。 |
| 并发、同步与线程安全 | 单所有者，无锁；`const&` 只限制本函数写入，不允许调用者同时修改输入。 |
| 单元测试与验证方法 | 覆盖两条分支、错误品种/模式、成功及各业务忽略的时间更新；逐字段比较输入前后，不用结构体 padding 做 `memcmp` 结论。 |

##### B. `Add`：为一张新限价订单建立完整关系

| 实现维度 | 具体方案 |
|---|---|
| 函数声明与职责 | `ApplyResult Add(const qlib::order& event)`；完成新增状态，自己不更新时间。 |
| 输入、输出与契约 | 只由合法逐笔 add 分支调用，限价新增量为正；成功为 `Applied/None`，市价、重复和总量越界分别返回约定忽略原因。 |
| 核心算法与数据结构 | 先查状态、再准备价位/hive/ID 资源，最后连接尾部。ID 索引只保存 hive 对象地址。 |
| 具体执行步骤 | ①市价返回 `MarketOrder`；②已有 ID 返回 `DuplicateId`；③查目标价位并做总量加法前检查，通过后执行容器容量的表示范围检查；④必要时创建空价位；⑤复制输入并清空链接，`orders_.emplace(copy)` 并取 `node=std::addressof(*iterator)`；⑥`by_id_.try_emplace(std::int64_t{event.order_id}, node)`；⑦`LinkOrders`；⑧返回成功。 |
| 成员读写 | 读取 ID/价位，新增一个 hive 对象和 ID 项，并更新一个价位及其原尾节点；不改绑定、最近时间和其他价位。 |
| 对其他函数的调用 | 容器 `find/try_emplace/emplace/erase`、`LinkOrders`；局部清理不调用要求“已挂链”的 `Erase`。 |
| 边界与错误处理 | 先用 `event.qty <= INT64_MAX - old_total` 判断，再计算和；越界忽略，不临时建立资源。不比较买卖价格来撮合。 |
| 异常安全与状态一致性 | 保存本次新价位标记和新 hive 迭代器。hive 或 ID 插入失败时先删本次对象，再删本次空价位，随后重新抛异常；旧业务状态不变，容量可变。重复预检后插入仍返回 false 属内部不一致，清理后报告，不能泄漏对象。 |
| 时间与空间复杂度 | 通常平均 `O(log L)`，ID 表扩容可搬动 `O(N)` 项；必要时分配价位、hive 块或 ID 表。新增逻辑对象为 1 个，块/表扩容的瞬时空间随容量变化。 |
| 并发、同步与线程安全 | 只在所有者线程内准备和提交；中间空价位不向其他线程暴露。 |
| 单元测试与验证方法 | 同价尾插、同 ID 忽略、市价、交叉价格不撮合、合计上界与越界、输入链接不被采用；第 5.3 节验证 hive 和 ID 插入失败后的无残留。 |

##### C. `Modify`：替换已有订单的价格或剩余总量

| 实现维度 | 具体方案 |
|---|---|
| 函数声明与职责 | `ApplyResult Modify(const qlib::order& event)`；按 ID 修改当前挂单，`new_qty` 表示新剩余总量。 |
| 输入、输出与契约 | 合法逐笔 modify；未知 ID 为 `Ignored/UnknownOrder`，方向冲突为 `Ignored/SideMismatch`；成功更新、删除或明确忽略，不创建未知订单。 |
| 核心算法与数据结构 | 同价只替换数量并保持链接；改价先准备目标价位，再把原节点移到目标尾部；非正新量删除。 |
| 具体执行步骤 | ①找节点，未知即返回；②先检查方向；③`new_qty<=0` 调用 `Erase`；④同价同量返回 `Unchanged`；⑤同价计算 `base=level.qty-node.qty`，检查新量后提交；⑥改价先查/建目标并检查总量，再解旧链、改 price/qty、接新尾。 |
| 成员读写 | 保留节点地址、ID、方向；只更新节点当前 price/qty、涉及价位和链接。原始新增的其他字段不被当作当前输入事件覆盖；最近时间由外层更新。 |
| 对其他函数的调用 | `FindLevel`、`Erase`、`UnlinkOrders`、`LinkOrders` 和价位容器操作。 |
| 边界与错误处理 | 方向冲突优先于删除，不能用负新量绕过方向规则。同价用 `new_qty <= INT64_MAX-base`，不先算可能溢出的差量；删除分支不使用无意义的新价格。 |
| 异常安全与状态一致性 | 新价位分配在旧状态完整时进行；分配失败不动原节点。准备成功后提交不分配；若准备后遇到内部不变量错误，清理本次空目标并报告，不能把程序错误当正常忽略。 |
| 时间与空间复杂度 | 常见平均 `O(log L)`；删除增加 `O(B)`；改入新价位分配 1 个价位节点，其他分支额外空间 `O(1)`。 |
| 并发、同步与线程安全 | 同价不解链，改价在一个所有者调用内完成；目标 `std::map` 迭代器可跨另一价位删除使用，不能跨目标本身删除。 |
| 单元测试与验证方法 | 10→6、同价增加仍保序、改入新/已有价位进入尾部、方向冲突、零负量删除、未知 ID、同价/目标总量边界；故障时比较完整状态和输入。 |

##### D. `OnTrade`：分别扣减成交中能找到的订单

| 实现维度 | 具体方案 |
|---|---|
| 函数声明与职责 | `ApplyResult OnTrade(const qlib::trade& event)`；逐笔模式处理外部成交，L2 只记录事件到达。 |
| 输入、输出与契约 | 品种相同、成交量为正，两个有效 ID 不同；0 表示该侧缺失。至少改动一单返回 `Applied/None`，双侧未知/缺失返回 `Ignored/UnknownOrder`，L2 返回 `Ignored/L2Trade`。 |
| 核心算法与数据结构 | 用两个 ID 独立调用 `Reduce`；不依据成交价格或成交方向重新寻找挂单。 |
| 具体执行步骤 | ①检查品种及有效模式；②若 L2，直接得忽略结果；③若 Mbo，先记录 `changed_buy=Reduce(...)`，再记录 `changed_sell=Reduce(...)`；④合并两个布尔值；⑤`Touch` 后返回。 |
| 成员读写 | 逐笔时通过扣减函数改变相关订单、索引和价位；L2 不动价位；两模式正常返回都更新最近时间。 |
| 对其他函数的调用 | `Reduce` 两次和 `Touch`。必须先执行两次再逻辑合并，不能写成短路 `Reduce(buy)\|\|Reduce(sell)`。 |
| 边界与错误处理 | 单侧未知不妨碍另一侧；超额成交删除而不出现负量；双侧相同有效 ID 的协议拒绝在 V2 验证，本函数依赖此前置条件。 |
| 异常安全与状态一致性 | 合法状态下扣减不分配，不会在第一侧已改后因第二侧分配失败留下半次更新。内部不变量已损坏时立即报告，不建立通用事务去“修复”损坏对象。 |
| 时间与空间复杂度 | 两次平均常数 ID 查找，加至多两次 `O(log L)` 价位查找；发生移除时每单增加 `O(B)`；额外空间 `O(1)`。 |
| 并发、同步与线程安全 | 双侧操作由同一个所有者连续执行，快照不会在中间读取；无原子或锁。 |
| 单元测试与验证方法 | 双侧都有、只有一侧、双方未知、0 缺失、恰好/超额成交；成交 side/price 不决定节点归属；L2 成交保持量且更新最近时间。 |

##### E. `OnCancel`：处理外部撤销量

| 实现维度 | 具体方案 |
|---|---|
| 函数声明与职责 | `ApplyResult OnCancel(const qlib::cancel& event)`；按 ID 减少或移除挂单。 |
| 输入、输出与契约 | 合法正撤销量、相同品种、`Mbo` 模式；找到返回成功，未知返回 `Ignored/UnknownOrder`；不覆盖输入 qty。 |
| 核心算法与数据结构 | 复用 `Reduce`，不再维护第二套删除算法。 |
| 具体执行步骤 | ①检查绑定和模式；②`Reduce(event.order_id,event.qty)`；③转换为结果；④`Touch`；⑤返回。 |
| 成员读写 | 通过 `Reduce` 修改挂单和价位；正常返回更新最近时间。 |
| 对其他函数的调用 | `Reduce`、`Touch`。 |
| 边界与错误处理 | 未知 ID 忽略；撤单 `side` 只作为事件元数据，使用存储订单自身方向定位价位；恰好和超额量均删除。 |
| 异常安全与状态一致性 | 契约检查先于修改；合法状态下无分配失败点。错误模式/品种不改变订单、价位或时间。 |
| 时间与空间复杂度 | 平均 `O(log L)`，删除再加 `O(B)`；额外空间 `O(1)`。 |
| 并发、同步与线程安全 | 只由所有者执行，输入在调用期间保持稳定。 |
| 单元测试与验证方法 | 10 撤 4 得 6，撤 10/大于 10 删除；删首、中、尾和唯一节点；未知 ID、反向元数据、原输入及最近时间。 |

##### F. `Reduce`：共用的部分扣减或全量删除

| 实现维度 | 具体方案 |
|---|---|
| 函数声明与职责 | `bool Reduce(std::int64_t order_id, std::int64_t qty)`；找到并改变一单返回 true，否则 false。 |
| 输入、输出与契约 | 内部输入 qty 严格为正；ID=0 表示跳过，普通 ID 按当前簿查找；不更新时间。 |
| 核心算法与数据结构 | 先比较扣减量和剩余量；小于则同步减节点与价位，大于等于则删除。 |
| 具体执行步骤 | ①0 直接 false；②查 ID，未知 false；③`qty>=node->qty` 调 `Erase` 后 true；④否则先 `FindLevel`，再令节点和价位各减 qty，返回 true。 |
| 成员读写 | 读取 ID 索引；写节点 qty 和价位 qty，或通过删除清理三处关系。 |
| 对其他函数的调用 | `by_id_.find`、`FindLevel`、`Erase`。 |
| 边界与错误处理 | 先比较保证减法不会下溢；部分减后节点仍为正，价位至少包含该剩余量。不能先把节点减成负数再决定删除。 |
| 异常安全与状态一致性 | 部分分支在第一次写入前取得价位，之后两次整数减法不抛；删除沿用 `Erase` 的前置验证。 |
| 时间与空间复杂度 | 平均 `O(log L)`，完全删除增加 `O(B)`；空间 `O(1)`，不分配。 |
| 并发、同步与线程安全 | 节点指针仅在当前调用使用；不保存 ID 表迭代器供下一次插入后使用。 |
| 单元测试与验证方法 | 从成交/撤单公开方法覆盖缺失、未知、部分、等量、超额分支；检查部分扣减不重排同价顺序。 |

##### G. `FindLevel`：只查找已有节点所属价位

##### H. `LinkOrders`：把已准备节点接到目标价位尾部

| 实现维度 | 具体方案 |
|---|---|
| 函数声明与职责 | `void LinkOrders(qlib::order* node, qlib::price_level& level, std::int64_t new_total) noexcept`；只提交链接和已检查的总量。 |
| 输入、输出与契约 | 节点存活且当前未挂链，目标价位已存在，方向/价格匹配，new_total 已在调用者检查；无返回值。 |
| 核心算法与数据结构 | 利用价位 tail 常数步尾插，不遍历同价订单。 |
| 具体执行步骤 | ①令 node.prev=旧 tail、node.next=null；②旧 tail 存在就写其 next，否则设置 head；③设置 tail=node；④设置 qty=new_total。 |

| 边界与错误处理 | 空目标设首尾为同一节点；非空目标保留原 head；错误前提由调用者和测试保障，不能在部分连接后再抛业务异常。 |

| 时间与空间复杂度 | `O(1)`、额外空间 `O(1)`。 |
| 并发、同步与线程安全 | 中间指针更新只对所有者可见；不用于跨线程共享链表。 |
| 单元测试与验证方法 | 空/非空价位尾插和改价尾插；检查首尾、反向链接、总量和同价顺序。 |

##### I. `UnlinkOrders`：解除价位关系但保留订单对象

| 实现维度 | 具体方案 |
|---|---|
| 函数声明与职责 | `void UnlinkOrders(qlib::order* node)`；从原价位移走存活节点，不删除 ID 和 hive 对象。 |
| 输入、输出与契约 | node 已在本簿正确价位中；返回后 node.prev/next 为空，原价位不再包含它。 |
| 核心算法与数据结构 | 先查原价位，调整邻居和首尾，再减掉节点完整剩余量；最后一单离开时删价位。 |
| 具体执行步骤 | ①从节点方向/价格找到 map 及价位；②验证所需前提；③前节点存在则改 next，否则改 head；④后节点存在则改 prev，否则改 tail；⑤减总量并清节点链接；⑥为空则 `erase` 该价位。 |
| 成员读写 | 修改原价位、相邻节点和本节点链接；不改节点 price/qty、不改 ID/hive。 |

| 边界与错误处理 | 首、中、尾、唯一节点分别处理；不允许“head 为空但总量非零”正常返回。缺失价位在任何写入前报告。 |
| 异常安全与状态一致性 | 查找和前提验证在提交之前；固定整数比较器、平凡价位析构下，链接赋值和迭代器删除不分配。不因无分配就无依据添加 `noexcept`。 |
| 时间与空间复杂度 | 查找 `O(log L)`、链接修改 `O(1)`；空间 `O(1)`。 |
| 并发、同步与线程安全 | 调用方在同一操作中立即重新挂链或销毁节点；未挂链状态不越过公开方法返回。 |
| 单元测试与验证方法 | 从改价和全量删除覆盖四种位置；原价位最后一单移走后不存在，其他价位和 ID 仍一致。 |

##### J. `Erase`：移除所有借用关系后销毁挂单

| 实现维度 | 具体方案 |
|---|---|
| 函数声明与职责 | `void Erase(qlib::order* node)`；完整移除一张活订单。 |
| 输入、输出与契约 | 指针来自本簿当前有效 ID 项，节点已挂链；返回后该指针无效，调用方不得再读任何字段。 |
| 核心算法与数据结构 | 先准备删除所需的当前容器位置，后依次解链、删除 ID、删除 hive 对象。 |
| 具体执行步骤 | ①保存 ID 并验证现有 ID/价位关系；②用当前 `orders_.get_iterator(node)` 取得本次合法迭代器；③`UnlinkOrders(node)`；④`by_id_.erase(id)`；⑤`orders_.erase(iterator)`；⑥不再访问 node。 |
| 成员读写 | 改价位及邻居、ID 表和订单存储；删除唯一节点时相应价位也删除。 |
| 对其他函数的调用 | `FindLevel`/同等前置检查、`UnlinkOrders`、`by_id_.erase`、`orders_.get_iterator/erase`。 |
| 边界与错误处理 | 不把 get_iterator 当指针有效性探测；只对已证明属于当前存储的活节点调用。移动前保存的 hive 迭代器不能复用。 |
| 异常安全与状态一致性 | 合法状态下，固定键哈希、比较器和记录析构使提交不分配且不抛；所有可报告的前提错误尽量在第一处写入前发现。没有“删除失败后重建订单”的补偿路径。 |
| 时间与空间复杂度 | 平均 ID 操作，加价位查找 `O(log L)` 与指针定位 `O(B)`；空间 `O(1)`。不得写成整体 `O(1)` 删除。 |
| 并发、同步与线程安全 | 无外部并发读节点；销毁后没有指针传到别的线程。 |
| 单元测试与验证方法 | 唯一/首/中/尾删除、连续删空、移动及外层扩容后的删除；ASan/UBSan 的实际执行按第 5 章记录。 |

##### N. `MemoryBytes`：计算不回绕的逻辑存储估计

| 实现维度 | 具体方案 |
|---|---|
| 函数声明与职责 | `std::size_t MemoryBytes() const noexcept`；返回口径固定的近似字节数。 |
| 输入、输出与契约 | 无参数，结果不是 RSS 或精确分配量；数学结果超出 `size_t` 时饱和为 `SIZE_MAX`，不得回绕成小值。 |
| 核心算法与数据结构 | 用 hive/ID 表容量和两侧价位数代入下方公式，不遍历订单。 |
| 具体执行步骤 | ①读两容量和两价位数；②每个乘法先检查上限；③每次累加先检查上限；④返回饱和值或真实可表示的估计。 |
| 成员读写 | 只读 `orders_`、`by_id_`、`bids_`、`asks_` 的容量/大小；无缓存字段需要同步维护。 |
| 对其他函数的调用 | 容器 `capacity/size`，实现文件内的饱和加法、乘法辅助函数。 |
| 边界与错误处理 | 空容器、容量已增长但订单减少、两侧数量相加、乘法和最终求和分别检查；不能先让中间算式溢出再检测。 |
| 异常安全与状态一致性 | 不分配、不抛、不改变业务状态；失败回滚允许容量变化，所以不能用此值完全相等作为业务回滚判据。 |
| 时间与空间复杂度 | 固定次数整数运算，时间和空间 `O(1)`。 |
| 并发、同步与线程安全 | 所有者读取当前容量；不允许 Metrics 线程直接读取本簿。 |
| 单元测试与验证方法 | 对实际容量/价位数逐项核对公式；内部 constexpr 饱和辅助函数用编译期断言检查纯整数边界，不能真申请接近 SIZE_MAX 的内存。 |

初始公式固定如下。`C_order`、`C_id` 分别是两个 qlib 容器的容量，`L_bid/L_ask` 是价位数，`sat_add/sat_mul` 分别表示遇到超界便返回 `SIZE_MAX` 的加法/乘法。

```text
order_bytes = sat_mul(C_order, sizeof(qlib::order))
id_slot_estimate = sizeof(IdMap::value_type) + sizeof(std::uint8_t)
id_bytes = sat_mul(C_id, id_slot_estimate)
level_node_estimate = sizeof(PriceLevelMap::value_type) + 4 * sizeof(void*)
level_count = sat_add(L_bid, L_ask)
level_bytes = sat_mul(level_count, level_node_estimate)
estimate = sat_add(sat_add(order_bytes, id_bytes), level_bytes)
```

ID 项包含键值对与每槽一个控制字节估计；价位节点沿用参考工程的“值加四个指针大小”估计，四个指针大小只是树节点管理/对齐余量，不是标准库承诺的真实布局。该公式不计 `Orderbook` 本体、分配器开销、hive 块/槽管理信息，且未精确覆盖树节点颜色/对齐。当前 qlib 的非空 ID 控制区实际为容量加 1 字节，公式未计额外哨兵字节及分配对齐。改变口径时必须同时更新说明和测试，不能把估计改称精确分配量。

#### 3.2.5 构造、初始化与资源释放

构造函数只绑定品种和模式，建立空容器，不生成订单、快照或后台任务。`BookMode` 非两种枚举值时抛出明确参数异常；合法构造后 `size()==0`，快照品种正确、两侧和时间为 0。容器是自动生命周期成员：构造期间发生异常时，由 C++ 自动销毁已完成构造的成员。

移动构造把存储块、索引表和价位树交给目标对象，活订单地址应保持不变。移动赋值先释放目标对象原有内容，再转交来源的全部拥有关系；默认成员赋值期间目标旧索引可短暂保存已经释放的地址，但其销毁不能解引用这些地址，且没有其他线程观察中间状态。按当前 qlib 的平凡指针值和标准价位析构，这一条件可核对成立。

移动保证必须验证两个方向：对象本身不会抛异常，内部订单地址仍指向转移后的存储。测试分别覆盖空/非空移动构造、给非空目标移动赋值，以及外层 map 扩容触发移动。来源对象移动后只要求可安全析构或接受新的移动赋值，不把继续处理事件、保留旧时间或自移动赋值写成本版保证。外层容器也不得依赖这些额外行为。

析构函数使用默认实现，不逐单调用业务 `Erase`，不触发快照、文件写入和日志异常。借用关系成员先结束，再由 hive 释放对象。测试观察到的指针只是临时证据，在对象销毁、该订单删除后不能再次解引用。

#### 3.2.6 类内部的关键实现流程

**新增的准备与提交。** 假设买价 100 已有 B1=10，再新增 B2=5：先查 B2 不存在，计算 10+5 可表示；建立 B2 的存储副本及 ID 项后，才让 B1.next 指向 B2、B2.prev 指向 B1，并把价位总量设为 15。若 ID 表分配失败，B1 和总量仍保持原样，删除尚未挂链的 B2 即可。若该事件同时创建了新价位，还要删除本次空价位。

**改价先准备目标。** B1 从 100 改到 101、剩余量变成 6 时，先确认 101 价位能容纳 6，必要时先分配价位。目标准备好后，100 价位去掉 B1 原量，再修改节点当前价格/数量，最后连接到 101 的尾部。这样分配失败不会把 B1 提前从旧价位移走。

**成交两侧独立执行。** B1 和 S1 各成交 2 时，先对 B1 扣 2，再对 S1 扣 2；任何一侧未知都不阻断另一侧。返回值表示这次调用是否至少改变一张订单，不表示发生了本地撮合。最后统一记录该条成交的时间。

**公开方法的共同结束点。** 业务 helper 得到 `Applied` 或 `Ignored` 后再 `Touch`；异常直接上抛。`Ignored` 只承诺订单和价位不变，不能让快照时间留在上一个事件。输入对象无论成功、忽略或异常都不由本类修改。

#### 3.2.7 类的实现顺序与依赖关系

1. 先定义结果枚举、绑定字段、容器别名和成员移动检查，再实现构造、空快照和两个观察方法，使数据关系先可检查。
2. 实现只做提交的 `LinkOrders`、局部资源清理和 `Add`，随后接入 `OnOrder` 的 add 分支，完成 V1-01。
3. 实现 `FindLevel`、`UnlinkOrders` 和 `Erase`，用删除/改价场景核对关系，再完成 `Modify` 和 V1-02。
4. 基于同一删除路径实现 `Reduce`、逐笔 `OnTrade`、`OnCancel`，完成 V1-03；不要复制两套扣减代码。
5. 实现 `OnLevel` 和 `OnTrade` 的 L2 分支，完成 V1-04；最后用组合、移动和失败回归完成 V1-05。新增/改价的失败边界应在写代码时实现，不推迟到最后才补回滚。

### 3.3 模块内部协作与调用流程

| 入口 | 主要调用顺序 | 正常返回前的共同步骤 |
|---|---|---|
| `OnOrder(add)` | 检查绑定 → `Add` → 准备容器项 → `LinkOrders`。 | 根据实际状态返回结果，调用 `Touch`。 |
| `OnOrder(modify)` | 检查绑定 → `Modify` → 同价更新，或目标准备后解链/接尾，或 `Erase`。 | 成功与业务忽略都 `Touch`。 |
| `OnTrade(Mbo)` | 检查绑定 → `Reduce(buy)` → `Reduce(sell)` → 合并结果。 | 只更新一次该成交的时间。 |
| `OnCancel` | 检查绑定 → `Reduce` → 部分减量或 `Erase`。 | 未知 ID 也更新时间。 |
| `OnLevel` / `OnTrade(L2)` | 前者直接设置/删除价位；后者不改量。 | 均更新本次事件时间。 |
| `OnSnapshot/size/MemoryBytes` | 直接读取当前状态。 | 不调用 `Touch`，不产生业务事件。 |

`ApplyResult` 不负责接纳计数、文件写入和失败广播。后续 Book 阶段不能因 `Ignored` 就丢弃原始记录；V1 只验证输入未被改写，并把这项跨版本要求保留在接口注释中。

### 3.4 模块关键算法的实现方案

**顺序与合计。** 同价链表的顺序是当前价位的到达顺序：新增接尾，同价修改保留位置，改价视为进入新价位并接尾。合计始终由每次局部修改同步维护，快照直接读合计。删除必须同时清理链表、ID 和存储，不能用“快照看起来正确”代替完整关系验证。

**安全整数运算。** 所有业务数量使用 `std::int64_t`，先证明算式安全再求值。新增检查 `qty <= INT64_MAX-total`；同价修改先计算非负 `base=total-old_qty`，再检查 `new_qty <= INT64_MAX-base`；部分扣减先比较 `qty < old_qty`，满足后才减。总量越界是业务忽略，内存估计越界则使用饱和返回，两者不能共用含糊的错误含义。

**饱和估计辅助函数。** `SaturatingAdd(a,b)` 用 `a > SIZE_MAX-b` 判断，`SaturatingMultiply(a,b)` 先处理任一值为 0，再用 `a > SIZE_MAX/b` 判断。两函数参数和返回均为 `std::size_t`，`noexcept`，无成员读写、分配和并发状态，时间空间均 `O(1)`。两函数实现为内部 `constexpr`，在同一源文件使用 `static_assert` 覆盖 0、1、上界、恰好可表示和超一的组合；运行测试另按真实容量核对整体公式。不为测试增加公共 API，也不复制另一份饱和算法来验证自己。

**容器容量的表示范围。** 业务数量检查通过后、开始新增准备前，使用当前容器容量做保守的整数表示检查。当前 qlib 的 ID 表首次分配容量为 8，增长可能翻倍；先证明现有容量不大于 `SIZE_MAX/2`，再求最坏的下一容量（空表取 8），并证明该容量不大于 `(SIZE_MAX-1)/(sizeof(IdMap::value_type)+1)`，覆盖槽位和“容量加 1”控制区所需字节。不能先求翻倍或字节乘积再检查。即使本次插入恰好不用增长，也可采用同一保守检查；这是防止超出机器可表示范围，不是另设业务订单上限。

当前固定版本 hive 的下一块容量是 `clamp(orders_.capacity(), 8, 8192)`；先证明当前容量不大于 `SIZE_MAX-next_block` 再调用可能新增块的操作，避免内部容量累加回绕。固定的 `qlib::order`、块上限 8192 和目标平台下，单块字节计算也应在接入核对中确认可表示；不得把该数字当作未来所有 qlib 版本都不变的保证。无法表示时抛 `std::length_error`，作为资源错误向上传播，保持业务状态；它与价位总量超界的 `Ignored/QuantityOverflow` 不同。检查逻辑采用内部纯整数谓词，以编译期边界断言核对，不用巨大实际分配验证。

**稳定地址与失效位置。** ID 索引中的值是订单地址，不是 hive 迭代器。hive 移动保留活对象地址，但迭代器带旧容器所有者，不能跨移动保存。外层 `qlib::map<std::uint32_t, Orderbook>` 插入后重新查找目标簿，不能继续用插入前保存的簿引用；测试必须真实观察容量变化来证明扩容发生。

### 3.5 模块并发与同步实现

本版没有工作线程，也不给 `Orderbook` 添加互斥锁。一个对象在一段使用期间只有一个所有者；公开更新、快照、计数和内存估计都串行调用。不同对象可以由不同所有者独立使用，但 V1 不以此扩展产品的并行建簿模型。

未来 V2 中 Book 线程拥有所有订单簿并发布原子指标，其他线程只消费值副本。`OnSnapshot() const` 仍不能与写线程同时执行；把一个方法声明为 `const` 并不能消除容器读写的数据竞争。移动或销毁对象前必须保证没有别的执行方使用其引用或内部地址。

### 3.6 模块错误处理与恢复方案

| 情况 | 处理动作 | 返回/异常后可以依赖的状态 |
|---|---|---|
| 重复、市价、未知、无变化、方向冲突、数量合计越界 | 返回对应 `Ignored`，正常执行时间更新。 | 订单、索引和价位未改；输入不变，最近事件元数据可能变化。 |
| L2 成交、删除不存在的 L2 价位 | 分别返回 `L2Trade`、`MissingLevel` 并更新时间。 | 聚合量不变，不能将其当作输入拒绝。 |
| 公开入口品种/模式不匹配 | 在更新前抛明确参数异常。 | 原业务状态和时间保持；此为内部调用错误，不增加 feed_dropped。 |
| 新增或新目标价位分配失败 | 撤销本次尚未提交的对象/空价位，再传播原异常。 | 已有订单、链接和价位量保持；容器容量允许变化。 |
| 已有节点找不到价位等不变量破坏 | 报告程序错误，停止本次正常处理。 | 不承诺从已损坏状态自动修复；不伪装成 `Ignored` 继续服务。 |

本模块不重试失败事件，不吞掉 `std::bad_alloc`，也不在 catch 中打印可能再次分配的大段日志。未来工作线程外层负责报告致命失败并停止链路。V1 的受控失败测试需先关闭注入，再做断言和诊断，证明局部回滚后对象能继续合法处理或安全析构。

### 4.2 类与关键函数的实现依赖

| 待实现能力 | 先具备的函数或数据 | 依赖原因 |
|---|---|---|
| 新增 | 容器、总量检查、`LinkOrders`、`Touch`。 | 对象、索引和价位准备齐全后才能无分配地提交链接。 |

| 同价修改 | 当前节点与价位总量、已校验的新总量。 | 数量变化不需要断开链接，也不能调整 FIFO。 |
| 改价 | 目标价位准备、`UnlinkOrders`、`LinkOrders`。 | 旧状态必须保留到新价位分配成功。 |

| 移动与失败测试 | 全部普通业务、只读观察器、固定容器版本。 | 测试必须比较完整业务状态，且失败点需要发生在真实准备阶段。 |

例如，`OnTrade` 应分别执行买方和卖方的 `Reduce`，最后合并“是否至少改变一张订单”的结果。不能写成 `Reduce(buy, qty) || Reduce(sell, qty)`，因为第一个为真时，C++ 会跳过第二次调用，造成只扣一侧。

### 4.4 实现中的主要风险与处理方案

| 风险 | 具体处理 | 如何发现遗漏 |
|---|---|---|
| 先改价位总量，再发生分配失败。 | 所有可能失败的准备先执行；链接和数量提交不再分配。 | 新增索引分配失败、改价新价位失败后核对全部订单、FIFO 与价位。 |
| 同价改单误当差量或重排。 | 使用绝对 `new_qty`；保留节点地址和链接。 | 同价至少两张订单，增量与减量分别检查顺序。 |
| 计算总量发生中间溢出。 | 先用减法得到安全的 base，再用上界减法检查新量；扣减先比较再相减。 | `INT64_MAX` 临界值及超额扣减，必要时用 UBSan。 |
| 外层表移动后仍用旧引用或 hive 迭代器。 | 插入后按品种重新查找，删除时向当前 hive 重新取迭代器。 | 扩容后继续改撤，显式移动构造和赋值分别验证。 |
| 只有 best1 正确，其他价位或链接已坏。 | 测试观察器检查全部价位、订单和 ID 对应，限制链表遍历次数。 | 固定混合序列每一步检查不变量，检测重复访问和环。 |
| 用单侧成交测试掩盖短路问题。 | 明确调用两次扣减，最后合并结果。 | 买卖两侧均存在且都需要变化的固定测试。 |
| 故障工具误伤测试框架，或没有命中实际分配。 | 独立可执行文件；短作用域开启，关闭后再做断言；检查实际注入次数。 | 对齐分配探针及第七单索引扩容夹具。 |

检查器用于查看节点地址、实际容量、ID 对应关系、链序和总量。它按以下顺序做检查；这些遍历只出现在测试中：

1. 收集 hive 中全部存活订单地址，再核对每个 ID 项都指向其中一个节点，键值等于节点订单 ID，订单数与索引项数相同。
2. 对每个价位从 head 前进到 tail；每次解引用前确认地址属于该簿的存活集合。检查相邻 prev/next 互相对应、节点方向和价格匹配，首尾外链为空。
3. 每条链最多访问该簿存活订单数个节点，超过即报告环；不能让错误链表把测试拖入无限循环。每张存活订单恰好出现在一个价位中。
4. 对每张订单先验证剩余量为正，再用受检加法计算价位总量；总量与 level.qty 相等，价位不能为空。L2 则检查订单存储和 ID 索引为空，各价位数量为正且无链指针。
5. 读取快照验证最优两侧、绑定品种和最近事件时间。快照只读且按值返回，后续改变订单簿不能改变已经取得的快照。

检查器不是另一套高性能容器，也不重复实现完整订单簿算法。输入期望主要来自短小固定序列及明确的逐步结果；不让预期值与生产实现共享同一段更新代码。

### 5.3 边界与异常测试

**整数边界与前置条件。** 新增及改单覆盖合计恰好等于 INT64_MAX 和再增加 1；同价修改从 `level.qty - old_qty` 得到 base，再检查新量，不能使用会先溢出的差量。非正 new_qty 和 L2 非正 qty 是合法删除语义。非正成交/撤销量、重复的两个有效成交 ID 属于 V2 输入拒绝范围，不把它们混入“已校验事件”的普通业务用例。模式和品种错误则是本版应明确验证的内部调用错误。

MemoryBytes 使用真实容量和价位个数核对正常公式；饱和加乘的内部 constexpr 辅助函数通过编译期断言覆盖 0、最大值、最大值加 1 和最大值乘 2。不要伪造 qlib 的私有容量、申请巨大内存或改坏容器来制造溢出路径。该估计允许因扩容或回滚后的容量变化而变化，失败回滚断言比较的是业务状态。

**受控分配失败机制。** 仅在 `qbook_allocation_tests` 中链接 `tests/support/AllocationFailure.cpp`，头声明放入同目录的 `AllocationFailure.h`。这份小型测试辅助代码替换全局普通及带 `std::align_val_t` 的 new/new[]，并提供相匹配的普通、带 size、带 alignment 及 nothrow 形式的分配/释放函数。正常生产目标和 `qbook_tests` 不链接这些替换，也不重新编译一份带故障分支的 Orderbook。

必须覆盖对齐分配：已核对的 qlib `hive::allocate_block` 和 `map::allocate` 都直接调用 `::operator new(bytes, std::align_val_t(...))`。只替换普通 new 不能证明这两处失败被覆盖；新价位的 `std::map` 节点则需要普通分配检查。

测试辅助代码按以下边界实现：

1. 用 thread_local 的简单计数、分配种类过滤和固定大小记录保存“下一次匹配分配失败”的状态；记录不使用 vector、string、日志或其他会再次分配的设施。
2. Linux/WSL2 基线下，普通分配转交 malloc，对齐分配转交 posix_memalign，释放转交 free；零字节按至少 1 字节处理。传给 posix_memalign 的对齐至少为 sizeof(void*)，并保持原要求的合法二次幂对齐。注入关闭时保持替换分配函数应有的语义：真实分配失败时按标准 new-handler 规则重试或抛出，nothrow 形式捕获后返回空指针；实现过程中不能递归调用被替换的 new。
3. 当匹配的分配被命中，先记录命中并自动关闭注入，再抛 std::bad_alloc；nothrow 形式相应返回空指针。只失败一次，避免异常展开期间的框架分配被再次干扰。作用域守卫在任何退出路径再次关闭并复位。
4. 构造事件、订单簿和全部期望值时保持注入关闭；只在一次 OnOrder/OnLevel 调用周围开启。try/catch 记录是否出现 bad_alloc，关闭作用域之后才执行 Catch2 断言、检查器和诊断格式化。
5. 专用程序的这些用例顺序执行，不在注入期间创建后台线程；不把同一个全局替换对象文件链接两次。辅助代码不能依赖替换分配函数自身来管理状态。
6. 先运行一个不开启失败的同路径探针，确认预期分配种类实际被观察到，再实施失败。容量、分配路径或标准库改变时重新核对夹具；“没有命中但程序没崩溃”不算通过。

不把“无抛出”断言写在开启注入的 Catch2 宏内，因为测试框架可能为断言消息分配内存。故障是否命中、异常类型、恢复后状态是三项独立证据。

| 故障用例 | 注入前的确定状态 | 精确命中方式 | 关闭注入后验证 |
|---|---|---|---|
| F-01 新增首个价位失败 | 空逐笔簿；合法限价新增。 | 下一次普通分配失败；确认命中新价位节点分配。 | 空簿保持、输入不变，无节点或索引；随后同一合法事件可成功。 |
| F-02 新增 hive 块失败 | 空逐笔簿；新增准备顺序为目标价位、hive、ID。 | 允许目标价位普通分配；下一次对齐分配失败，命中 hive 块。 | 本次临时空价位清除，hive 与 ID 索引均空；随后可继续使用。 |
| F-03 hive 对象创建后 ID 扩容失败 | 同一价位已有 6 单；检查锁定 qlib 下 ID 容量为 8、hive 容量为 8，尚无删除墓碑。 | 第 7 单复用现有 hive 空槽且不新增价位；ID 表超过 3/4 负载，需要扩为 16，下一次对齐分配失败。 | 原 6 单、地址、数量、链次序和价位总量完整；第 7 个 hive 对象已回收、ID 不存在；重试可成功。 |
| F-04 改价目标准备失败 | 旧价位至少一单，目标价格尚不存在，new_qty 合法。 | 下一次普通分配失败，命中新目标价位节点。 | 旧节点地址、价格、数量、首尾和总量原样；无新价位，随后改价成功。 |
| F-05 L2 新价位失败 | L2 簿已有其他价位，目标价位不存在。 | 下一次普通分配失败。 | 既有价位和订单数 0 保持，无空目标价位，随后设置成功。 |

F-03 的 6/8/16 是根据当前 qlib 的最小容量与负载规则选择的**测试夹具**，不是 qbook 公共业务常量。固定依赖实际不符时，先依照新容量和负载条件重建可解释的夹具，再更新记录；不能在命中不确定时继续宣布关键回滚已验证。F-02 与 F-03 都必须检查 hive 活对象数，单看最优快照无法发现孤立对象。

所有失败用例保存调用前的业务摘要和输入，之后检查状态一致与可继续使用；容器容量无需相等，致命异常后的最近事件时间不作为契约通过条件。这里继续调用是为了证明局部回滚和对象有效，不意味着完整服务遇到 bad_alloc 后应自动继续接收行情；未来运行阶段仍按致命失败退出。

**移动与生命周期诊断。** 在支持 ASan/UBSan 的实际工具链中，对 V1-05 的移动、扩容、删除和整数边界运行一次组合诊断。AddressSanitizer 检测越界、释放后使用等内存错误，UndefinedBehaviorSanitizer 检测有符号溢出等未定义行为。改变编译和链接插桩需要独立缓存，所以允许一个 `build/v1-sanitize`；它不是日常第二套构建目录。

先确认目录是本次新建、工具链支持参数，再执行：

```bash
cmake -S . -B build/v1-sanitize -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug \
  -DBUILD_TESTING=ON \
  -DQBOOK_BUILD_SERVICE=OFF \
  -DQBOOK_BUILD_BENCHMARKS=OFF \
  -DQLIB_BUILD_TESTS=OFF \
  -DCMAKE_CXX_FLAGS="-fsanitize=address,undefined -fno-omit-frame-pointer" \
  -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address,undefined"

cmake --build build/v1-sanitize --parallel
ASAN_OPTIONS=halt_on_error=1 \
UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1 \
ctest --test-dir build/v1-sanitize --output-on-failure --no-tests=error
```

插桩应覆盖 qbook_core 和测试，不能只检查未插桩的测试壳。全局分配替换与 sanitizer 在选定工具链的兼容性需先确认；若专用故障程序出现工具冲突，保留该证据，明确将其故障用例在标准构建运行，并用正常业务程序完成生命周期诊断，分别记录实际范围。不要以工具冲突为由省略普通构建的关键失败用例。环境确实不支持诊断时写明原因与未执行项，不伪造通过，也不未经依据增加 TSan、多编译器或全配置矩阵。

### 5.4 性能测试与测量方法

V1 不添加 benchmark 或 perf 实验，不设置未经确认的吞吐、延迟门槛，也不把 Catch2 用例耗时当成订单处理性能。本版验证可见的成本边界，为 V5 留出可靠被测对象：

| 路径 | 本版检查内容 | 后续测量时需要区分的成本 |
|---|---|---|
| ID 查找 | 使用 ID 索引，不扫描全部订单。 | 平均查找与冲突、扩容的差异。 |
| 新增/改价 | 价位查找采用有序树，提交链接无隐藏分配。 | 新价位/新块/哈希扩容与已有资源路径。 |
| 删除 | 明确当前 hive 指针定位为 O(B)，B 为块数。 | 块定位、解链、ID 删除及释放空块分别可能产生的成本。 |
| OnSnapshot | 深度为 1，读取两侧边界价位，不遍历订单。 | 单簿快照与未来遍历所有品种、输出排队是不同计时范围。 |
| MemoryBytes | 读取容量、个数并进行固定数量的饱和运算。 | 这是估计公式，不是 RSS、分配器统计或延迟测量。 |

必要时用测试分配观察证明修改已有数量、部分扣减和快照没有引入意外分配；观察应围绕具体路径，不建立新的性能框架。若出现可复现的异常耗时，先记录输入规模和路径并排查，不提前声称优化收益。正式 Release 基准、种子、采样范围和目标机器仍由 V5 规划落实。

## 6. Plan Review（实现方案复核）

### 6.1 是否覆盖 Spec 中的设计

本计划覆盖 `specs.md` 4.3.2.1 的全部 Orderbook 公开入口、私有协作、成员所有权、构造销毁、移动和观察口径，并把 V1-01～V1-05 分别落实到源码、测试及验收。第三章写实现方法，第五章给出具体证据要求；两者都不能替代实际执行。

`specs.md` 4.3.2.2 的 BookThread 不在本版实现。FR-10 的周期、FR-11 的记录转交与文件保存、FR-13/14 的阶段指标尚未完成；本版仅为其提供可调用的状态组件、输入不变保证和 `size/MemoryBytes` 观察方法。AC-03～AC-08 中属于网络拒绝或落盘的条款仍要后续端到端验证。

### 6.2 算法与数据结构是否可行

该方案与已核对的 qlib API 相符：hive 为活订单提供稳定地址；ID map 借用这些地址；标准有序映射提供按价格组织的价位。订单只拥有一份，删除时的责任明确。新增与改价将分配放在提交之前，不需要每次复制整本簿，也不需要通用事务系统。

默认移动的可行性来自成员实际转交存储，而非函数上写了 `noexcept`。成员移动构造、移动赋值和实际销毁行为必须核对；外层 qlib map 使用的策略也必须满足其不抛异常契约。若实际锁定依赖与本计划不符，先调整和记录对应设计，再更改实现，不能通过隐藏异常来保留声明。

当前 `hive::get_iterator(pointer)` 会查找所属块，删除不能声称严格 O(1)。`MemoryBytes` 是可解释的粗略估计，通过饱和加乘避免回绕；它既不是进程 RSS，也不作为已证明的内存上限。第 3 章固定公式后，代码注释、测试和后续指标说明必须使用同一口径。

### 6.3 依赖与编码顺序是否合理

V0 提供真实可编译的公共类型和测试基础；V1 先建立可观察的新增状态，再加入改单、扣减和 L2，最后检验它们在移动和失败时的组合行为。这个顺序能尽早发现所有权错误，且不会被 ZMQ、Arrow、UI 等尚未引入的依赖阻塞。

V1-01 创建 `qbook_core` 时已有真实 `Orderbook.cpp`；五个普通业务测试文件按任务加入，分配失败工具在 V1-05 单独链接到专用测试进程。常规构建复用同一个目录，不将每项任务当成一个需要全新依赖下载和全新构建树的项目。

### 6.4 性能、资源与线程安全风险

| 方面 | 本版处理 | 仍然存在的限制 |
|---|---|---|
| 性能 | 保持 ID 查找、价位维护和常数深度快照，明确扩容及块定位成本。 | 没有吞吐或尾延迟实测；性能数值仍由 V5 评估。 |
| 内存 | 单份订单存储、局部准备回滚、容量算术检查与饱和估计。 | 活跃订单和价位可随输入增长；不存在业务上限或自动驱逐。 |
| 异常 | 区分业务忽略、程序契约错误和资源失败；对新增/改价准备保证业务回滚。 | 不承诺内存不足后服务继续运行；容量可以变化，异常后至少可安全销毁。 |
| 生命周期 | 删除先解除引用关系；移动保持节点地址但重新取得容器迭代器。 | 所有指针和引用只在所有者范围内使用，不能交给未来监控线程。 |
| 并发 | 组件单线程访问，无业务锁和共享写入。 | `const` 快照不代表能与写入并发；多线程调用属于契约违背。 |
| 故障验证 | 测试专用分配替换覆盖普通及对齐分配，关闭后检查完整状态。 | 如果目标工具链无法支持该手段，需要明确替代证据；未命中不能记为通过。 |
